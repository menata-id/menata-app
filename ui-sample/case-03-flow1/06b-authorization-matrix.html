Authorization Matrix

What each role may do in one Application, and what the Workspace decides instead. Every row is re-projected from a declaration the server already enforces — this page adds no permission model of its own. A ✓ answers the role question only; a rule that also narrows which record is spelled out under the row.

Transitions

A named move of a status field from one value to another, and the action that performs it. A row marked System is derived by the runtime — no role can be granted it, which is a different statement from a row where no role has been granted yet.

Record actions

Creating, editing and deleting records of this Application’s own Machines. These are governed by the same Permission primitive as a transition, and until this board nothing ever drew them — which is how two of the rows below stayed open without anyone noticing.

RULEAPPROVERSUBMITTERREVIEWER
Create a DocumentDocument · createAlso: only in your own name — the record must name you as its submitter.
Edit / delete a DocumentDocument · edit, deleteNo rule declared yet, so anyone may. This is the open one — it waits on every existing Document having an owner.
Create an Approval StepApproval Step · createNo rule declared: “only this Document’s submitter may add steps to it” is a cross-record rule this runtime cannot state yet.
Edit / delete an Approval StepApproval Step · edit, deleteAlso: only the step’s own approver, and only while it is still pending.
Keep a signatureSignature · create, edit, deleteDeliberately no role: owning your own signature is not a privilege. Only your own — the record must name you as owner.

Decided by the Workspace, not by this Application

Some rules are not an Application’s to make. A role vocabulary is declared per Application; administering the Workspace is not, and an audit trail belongs to no one at all.

No one, including an admin. Declared append_only: an audit trail is never changed or removed once written.

✓ the role satisfies every Permission governing this rule · · no grant. Several roles on one Permission are alternatives — hold any one; several Permissions on one action are requirements — pass all. Holding Workspace admin grants nothing here that a rule has not asked for: there is no bypass, deliberately, because an administrator who can approve a document they are not an approver of is the audit hole an approval flow exists to close.
