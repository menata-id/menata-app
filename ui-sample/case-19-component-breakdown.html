COMPOSABLE UI · 001–007

UI Composition & Metadata Breakdown

Every mockup is authored as a generic experience tree: Page → Layout → Component (007 §12). Layout is one generic structural primitive whose kind spans section, columns, grid, stack, split, tabs, and panel — there is no separate fixed "Column" node type in the runtime vocabulary. Component describes reusable UI capability; Dataset, Projection and a View Model provide semantic data (007 §7, §10); behavior remains outside the visual tree, expressed through the Behavioral Model — Event → Action → Permission/Constraint → Service/Data operation → State change (006 "Behavioral Model").

The composition model

E0 · §12.1
Page

Experience root. Should not own business logic.

E1 · §12.2
Layout

Generic spatial composition primitive. kind: section, columns, grid, stack, split, tabs, panel.

E2 · §12.3
Component

Reusable semantic presentation primitive with a bounded contract.

§12.4–12.6
View · Slot · Static Content

Supporting Experience-plane concepts: a precomposed presentation contract, a named extension point, and first-class non-data content.

Page
└── Layout · kind=section
    ├── Layout · kind=columns
    │   └── Component
    └── Layout · kind=columns
        └── Component

No BoardLayout, DashboardLayout, TaskTemplate, or other domain-shaped layout primitive is required — the runtime should not require separate layout concepts when their behavior can be expressed through generic Layout kinds (007 §12.2).

Visual decomposition and Runtime Metadata for the 11 mockup pages

Each wireframe shows the structural tree that its Runtime Metadata authors directly beneath it. IDs are stable references; children expresses composition; binding connects semantic data. The exact serialization may evolve while the normalized model (007) remains the contract.

How this maps to today's real, authorable metadata

The Page → Layout(kind) → Component tree above is the 007/006 composable target shape. The generic Layout kind vocabulary (columns/grid/stack/split/tabs/panel beyond main/aside) is tracked as not yet built: "Layout vocabulary beyond main/aside — §12.2 — 🟡 PARTIAL — CAP-V10 Tier 2 ships the one pairing; stack/grid/columns extensions are CR-tracked design triggers, not yet built" (007 §40 Claim Citation Matrix). guides/writing-runtime-metadata.md is correct not to document that vocabulary yet — a writing guide should describe real, loadable, validated metadata, not an unbuilt target.

What is real and loadable today is the Views children mechanism: view / content / component+dataset_id, laid out with layout: main/aside (CAP-V20, CAP-V10, CR-21/17k — see guides/writing-runtime-metadata.md §"Komposisi View" and §"View tipe page"). Mockup 06 (Sprint Dashboard/Insights) above, expressed in that real shape today:

views:
  - id: vw_insights_page
    type: page
    children:
      - component: Metric
        dataset_id: ds_sprint_open_count
        title: Open
      - component: Metric
        dataset_id: ds_sprint_done_count
        title: Done
      - view: vw_insights_chart
        title: Insights
        layout: main
      - view: vw_insights_attention
        title: Attention
        layout: aside

No addition to guides/writing-runtime-metadata.md is needed for this experiment — the gap is a not-yet-built runtime capability (007 §40, CR-tracked), not an undocumented one. The guide should gain a Layout-kind section only once that capability actually ships.

Binding semantic data to the visual tree

A Component should not consume raw records directly. The pipeline is Query → Projection → View Model → Component (007 §10); the View Model insulates the Component from whether a value came from a field, an expression, or a joined relation.

data:
  dataset: task.items
  projection:
    - id: title
      source: name
      semantic_type: title
    - id: status
      source: status
      semantic_type: status
    - id: person
      source: assignee
      semantic_type: person
    - id: date
      source: due_date
      semantic_type: date

view_model:
  title: $projection.title
  status: $projection.status
  person: $projection.person
  date: $projection.date

experience:
  type: Component
  component: ItemCard
  binding:
    title: { dataset: task.items, value: view_model.title }
    status: { dataset: task.items, value: view_model.status }
    person: { dataset: task.items, value: view_model.person }
    date: { dataset: task.items, value: view_model.date }

The same ItemCard can consume another Projection in HR, CRM, finance, document approval, or another domain. Behavior such as move, archive, approve, or reorder is referenced separately through the Behavioral Model — Event → Action → Permission/Constraint → Service/Data operation → State change (006 "Behavioral Model") — not the visual composition tree.

Component contract

A Component MUST expose a bounded semantic contract — it does not become "generic" merely by accepting arbitrary properties or silently performing arbitrary data access (007 §12.3, §13). Every Component referenced above (Header, StatTile, ItemCard, GroupContainer, …) is expected to declare its identity, inputs, data requirements, child slots, actions/events, accessibility semantics, and renderer implementation:

component:
  id: ItemCard
  inputs: [title, status, person, date]
  dataRequirements: [task.items]
  childSlots: []
  actionsEvents: [move, archive, approve]
  accessibility: { role: article }
  renderer: itemCard.renderer

Contracts should be versionable; breaking contract changes require explicit compatibility handling rather than silently changing the meaning of existing metadata (007 §13).

Runtime realization

Metadata declares semantic intent. The runtime parses, validates, normalizes and resolves references, then lowers the logical composition into UI IR and an execution/render plan. The author does not need to describe HTML/CSS or a framework-specific layout template.
